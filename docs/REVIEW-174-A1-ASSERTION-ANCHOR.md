它回答三件：[审的是什么]、[加了什么判据]、[这些判据能不能自己站住]。

> 本文件里的套件条数由 `tools/run_ci_wiring_guard.sh` 的判据⑤ 与

## 一、一句话结论

**本仓库 1131 条判据里，有 785 条是 `grep` 断言 —— 而此前没有任何一件东西问过
「这条断言的 pattern 真的能命中源码吗」。**

新增 `tools/run_assertion_anchor_guard.py`（8 条）+ 自测（8 条），把这件事补上。
它当场抓到 **3 处"死支"**（全是 `||` 后面的空判据，靠兜底撑着绿），并已修。

---

## 二、为什么单列这一格

`grep -q 'PAT' $FILE` 是本仓库判据的主力形态，它有一个**自己看不见**的坏法：

> `PAT` 在文件里一个都不命中时，这条断言再没问过任何问题。
> 正向位置（`grep -q`）下它**恒红** —— 有人 `|| true` 掉，彻底失效；
> 负向位置（`! grep -q`）下它**恒绿** —— "不出现"永远成立，等于没写。

两类都**静默**：守卫照样打印 PASS/FAIL，只是那一条的信息量是 0。
本仓库栽过同款（`0.9.142` 那个多打的方括号），而**判据网里没有一件东西**
问过"这条断言真的能命中吗" —— 这一格补的就是它。

## 四、加了什么（判据清单）

`tools/run_assertion_anchor_guard.py`（8 条）：

| 判据 | 防的坏法 |
|---|---|
| 每条正向 grep 断言都能命中 | pattern 打错/源码改了没改判据 → 恒红后被 `|| true` 抹掉 |
| 带负向断言的守卫都有双向自测 | 负向断言"能被打脸"只有靠自测打桩证明；没有自测就是"永不触发" |
| 计数类断言的阈值由非注释行满足 | `grep -c` 连注释一起数，阈值被说明文字撑到 = 替注释站岗 |

**怎么做出来的**：把每个守卫**真跑一遍**，用记账 shim 换掉 `grep`，拿到它
**真实收到**的 pattern（shell 两层转义之后）。

⚠ 这一条是**走出来的**：第一版让 python 自己静态解析 pattern，结果把
`-E` 模式、`\\"`、`\\\\`、反引号全多算一层，**误报 46 条假"零命中"**。
只有让 sh 自己展开才对得上。同理，**必须沿用原断言的 grep 模式**（BRE / ERE 两种语言），
不带 flags 复核会把所有 `-E` 判据误报成零命中。

## 五、它当场抓到的 3 处"死支"（已修）

三条都是 `A || B` 的形状，其中 `A` 早已不命中、整条判据一直靠 `B` 兜底撑着绿。
**它们"看着在守一件事"，实际那件事已经没有判据了。**

| 守卫 | 死支 pattern | 真相 | 修法 |
|---|---|---|---|
| `run_stop_match_guard.sh` | `回退不得越过` | 源码里从没这五个字连写 | 锚到现文`若回退越过` |
| `run_schema_sampler_guard.sh` | `snprintf(... "%08zx", genSuffix.size())` | 这正是同文件下一条判据明令**不许出现**的旧写法 | 锚到现文`utf16_len(genSuffix)` |
| `run_auth_guard.sh` | `带鉴权` | README 里从没这个词 | 锚到现文`一律免鉴权` |

修法一律是**把锚点移到源码现文上**（不是删掉死支 —— 判据要守的那件事仍在，
只是锚错了位置）。

## 六、判据能不能自己站住（双向自测）

`tools/run_assertion_anchor_guard_tests.sh`（8 条）—— 拿 3 份**就地改坏的真守卫**跑，
断言"该红的红、指得出是哪一条、还原后全绿"。桩全是真会写出来的坏法：

| 桩 | 坏法 |
|---|---|
| ① | 正向断言 pattern 打错一个字符 → 恒红/恒静默 |
| ② | 带负向断言的守卫删掉自测 → 那条"不出现"再没东西能触发 |
| ③ | 计数断言阈值被注释撑到 → 判据替说明文字站岗 |

为什么必须有：本守卫是"跑别人"的，三个自欺方向都不报错 —— 判宽了恒绿（复核时
忘记带 `-E` 就把 ERE 判据全误报，第一版真踩到）、判窄了恒红（有人 `|| true` 掉）、
锚错位置（钉"文件里出现过 pattern"而不是"这条断言指向的 pattern 命中了"）。

---

## 七、明确没做的事

- **只改判据，不改被审的源码**：3 处死支改的都是**守卫里的锚点**，`app/` 下一个字节没动。
- **判不了"命中之后逻辑对不对"**：本守卫只回答"这条 pattern 能不能命中"。
  命中之后的语义正确性要靠各守卫自己的双向自测 —— 边界写在守卫文件头。
- **没做双壳同义的全量扩面**：方案里判据①（把"逐行比 `sh` 与 `bash`"扩到全部纯静态
  守卫）**已在 2 轮前由 `run_ci_wiring_guard.sh` 实现**（CI 的静态守卫在 sh / bash 下
  输出逐行相同），本轮不重复造。
- **没做 `trap` 补全**：方案里那条"`run_*_guard_tests.sh` 缺退出即还原的 `trap`"
  属甲-1 前置，但**本轮实测发现全仓库 35 份自测都已有 `trap ... EXIT`**，
  这条前置已不成立，故不再单列。
- **顺手发现、本轮不修的一处**：`run_schema_sampler_guard_tests.sh` 的桩⑦
  已经**与源码漂移**（它锚 `nativeNewSampler(...thinkingOn: Boolean): Boolean` 的旧尾参，
  而源码早加了 `biasIds, biasVals`），于是桩⑦ 自己报 `没找到 native 声明` 并**整份自测中止**。
  这不属甲-1 范围（是本守卫的自测桩过时，与"断言能不能命中"是另一件事），
  登记在此备查 —— 换句话说：**这份自测实际只跑了桩①~⑥，桩⑦以后全没跑**，
  正是甲-1 要防的"判据没被执行"的另一形态（这次在自测桩这一层）。

## 八、接入

- 守卫接进 `.cnb.yml`（`/health` 守卫之后），纯 python3 标准库 + sh，不依赖工具链；
- **总时限**：守卫对 40 份守卫各真跑一遍、再对每条判据全仓 grep，本机实测约 5 分钟。
  给了它一个上限 —— 默认 `600s`（实测两倍余量），`ASSERTION_ANCHOR_TIMEOUT=<秒>` 可覆盖、`0` 关闭，
  `.cnb.yml` 里显式置 `600`。超时**明确红并指出是哪一步**，而不是静默挂死
  （挂死的形态与"还在跑"同形）。`ledger` 子进程另有 `ASSERTION_ANCHOR_LEDGER_TIMEOUT`（默认 180s）单份兜底。
- 自测接进 `.cnb.yml`（请求边界守卫自测之后）；
- 两份条数落进 `tools/suite-counts.json`，由 `run_ci_wiring_guard.sh` 判据①③⑤⑦ 约束。

| 套件 | 条数 |

| `tools/run_assertion_anchor_guard_tests.sh` | **9 条**（上一份的自测；v2 加「真源码未被本测试改动」的第 9 条，见下） |

## 九、v2（2026-10-02）：自测改成"真源码只读"

### 9.1 病：这套自测自己的打桩机制会漏桩

v1 的自测用"就地改真源码 + `trap` 还原"：`cp` 备份到 `$TMP`，`sed` 改真守卫，
`trap restore EXIT INT TERM HUP` 收工还原。当时已经知道要 trap 满四个信号
（#126 那轮脏工作区的机制），但**加了信号也堵不住**，有两条不同的漏法：

- **SIGKILL**：`.cnb.yml` 的 `timeout`、`count_suite_totals.py` 的
  `subprocess.run(timeout=)`、OOM killer —— 都发 SIGKILL，**它不可捕获**，
  任何 `trap` 都不执行；
- **`$TMP` 被回收**：`restore` 依赖 `$TMP/*.bak` 还在。`/tmp` 被清理（或
  `mktemp -d` 的目录被别的清理进程收走）之后，`cp "$TMP/x.bak" …` 失败，
  `set -e` 下 `restore` **半途死掉** —— 前面几个文件还原了、后面的没有。

两条路径后果相同：桩留在工作区。而下一轮的人看到的是"守卫莫名变红"。

### 9.2 观测到的实例（这就是它不止是理论的原因）

`count_suite_totals.py --check` 的 `measure()` 用 `subprocess.run(timeout=300)` 跑每个套件。
**超时即 SIGKILL。** 实测一次 `--check` 之后，工作区留下：

```
 M app/src/main/cpp/llama_jni.cpp      (被清成 0 字节，原 278302)
 M app/src/main/java/.../HttpApi.kt    (1 行)
 M app/src/main/java/.../LlmEngine.kt  (1 行)
```

这几处的形态正是各 `_guard_tests.sh` 的桩。也就是说：**CI 的快检门禁
本身是这套漏桩机制的触发点**，不是"偶发被强杀"。

### 9.3 修法：不修 trap，改成不需要还原

靠把 trap 写得更严密是修不掉根因的 —— SIGKILL 无法捕获，而"还原"依赖一件
随时可能消失的东西（`$TMP`）。所以换判据：**真源码只读**。

- 全部打桩发生在 `$WORK`（一份完整工作副本）里，`guard` 也从副本里跑
  （`run_assertion_anchor_guard.py` 的 `ROOT` 按脚本自身位置推导，副本自洽）；
- 副本内的复位基线放在**副本自己**里，不依赖 `$WORK` 之外任何东西；
- **故意不装清理 trap**：副本留在 `/tmp` 无害（真源码没被动过），
  而清理一旦失败又是一条会静默失效的路径 —— 正是 v1 的死法。
  宁可泄漏几 MB，也不要一条"看起来该跑却没跑"的清理。

于是"忘了还原"这件事**在物理上不可能发生**：没有东西需要还原。

### 9.4 第 9 条判据：让"漏桩"当场可见

只让漏桩不可能还不够 —— 得让**将来任何**重新引入的就地打桩当场露馅。
新增收工判据：把 4 个被 watch 的真源码文件做一份 `sha256` 汇总指纹，
开工记一次、收工比一次，不等就红。

这条判据的语义是"根因判据"：**v1 的漏桩在此处必然变红**（因为 v1 的桩
就打在真源码上，指纹必然变了）。而 v2 里它恒绿，因为真源码只读。

另有一条更早的信号：真源码树上**基线本身就是红的**（本次实测时
`llama_jni.cpp` 已是 0 字节 → 基线 FAIL）。这不改变结论 —— 它是被测的"缺陷"
而非"测试的噪声"，但足以让人立刻知道"先去看工作区，别怀疑判据"。

### 9.5 附带：账目与快检预算

- 本自测条数 **8 → 9**（`tools/suite-counts.json` + 本文件条数表）；
- `count_suite_totals.py` 新增 `SLOW_SUITES`：本自测要跑 4 轮守卫、合计约
  **18 分钟**，快检（`--check --static-only`）给它的 300s 预算必然把它 kill 成
  `实测=None`，对着清单里的真值就是一条**假漂移** —— 这正是它长期挂在
  `实测=None` 上的原因。`SLOW_SUITES` 与 `toolchain_dependent()` 并列
  （都是"快检这台机器上量不动"），但判据不同：那里缺工具链，这里缺时间预算。
  列进去的套件不失去保障，只是不进快检的逐套件对账；非快检的 `--check`
  仍然核对它。

### 9.6 验证

- **SIGKILL 路径**：起自测、8s 后 `kill -9` → `git status` 干净、
  4 个被打桩文件的桩标记全为 0、指纹不变；
- **`$TMP` 回收路径**：起自测、10s 后 `rm -rf` 副本目录 → 真源码零改动
  （脚本报 FAIL，因为它的工作面没了 —— 但它污染不了真源码）；
- **正向路径**：副本里跑完整自测 → **PASS 9 / FAIL 0**，指纹前后一致
  （`c1289db2…` → `c1289db2…`）；
- `sh tools/run_ci_wiring_guard.sh` → **PASS 18 / FAIL 0**（判据⑤ 文档与清单同源）；
- `python3 tools/count_suite_totals.py --check-total` → 套件总数一致（130 个）。
