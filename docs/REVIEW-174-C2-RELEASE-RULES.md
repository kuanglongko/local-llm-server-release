# Issue #174 / 模块丙-2：发布链自检（收口）

本文件是 **Issue #174「代码自检」模块丙-2** 的收口结论。
它回答三件：[审的是什么]、[加了什么判据]、[这些判据能不能自己站住]。

> 议题背景与分模块方案的原始记录在 Issue #174 的评论里（本文件只做收口）。
> 本文件里的套件条数由 `tools/run_ci_wiring_guard.sh` 的判据⑤ 与
> `tools/suite-counts.json` 逐条钉住 —— 本文的数字和别的文档受同一把尺子约束。

---

## 一、一句话结论

`release-rules.json` 的规则按 **`old -> new` 精确文本匹配**清洗发布物。
`old` 在源码里不再出现时，`replace` **什么也不做、不报错、不告警** ——
规则死了而发布照跑，**该清洗的开发痕迹直接进发布线**。

新增 `tools/run_release_rules_guard.py`（8 条）+ 自测（8 条），把"活跃 / 已应用 / 失效"
三态分开。**它当场抓到 1 条失效规则**（源码又改过一遍，规则再也命不中），已修。

---

## 二、为什么单列这一格

方案里这一格的症状写得很准：**"规则靠精确匹配旧文本 → 漏清洗不报错，直接进发布线"**。

具体的静默链条：

1. 规则 `R` 把开发期文本 `old` 清洗成发布态 `new`；
2. 之后有人**又改了一遍**那段文本（`new` 被编辑成 `new'`）；
3. 下次发布时：`R.old` 不在源码里 → `replace` 空转 → **`new'` 里的开发痕迹没人清**；
4. 发布器**照常跑完、照常出发布物**，人看到的是一份"规则齐全、门禁通过"的产物。

`release.py` 有 `selfcheck_hygiene`（把规则套到产物上再过门禁），但它**判的是
"清洗后还有没有残留"，不判"这条规则还活着吗"** —— 规则已死时它同样静默。

---

## 三、审到的现状（本机实测）

```
规则 14 条：活跃 6 / 已应用 7 / 失效 1
规则基线   = 78aa39a，落后 179 个提交（其中若干动过被清洗文件）
```

三态的判法与理由：

| 状态 | 判据 | 含义 |
|---|---|---|
| **活跃** | `old` 在源码里 | 规则正常工作 |
| **已应用** | `old` 不在、`new` 在 | 源码已是发布态，规则幂等空转（**无害**） |
| **失效** | `old`、`new` **都不在** | 源码后来改过一遍，规则**再也命不中** = 静默漏清洗 |

> 只判"`old` 在不在"会把 **7 条已应用**误报成死的；只判"`new` 在不在"会把
> **6 条活跃**误报成死的。三态必须分开。

---

## 四、加了什么（判据清单）

`tools/run_release_rules_guard.py`（8 条）：

| 判据 | 防的坏法 |
|---|---|
| 规则集非空 | 规则被清空 → 全部静默 |
| 每条规则的 `path` 都存在 | 路径写错/文件改名 → 规则永远空转 |
| **没有失效的规则**（`old`/`new` 都不在） | 源码演进后规则死掉 → 漏清洗进发布线 |
| 没有重复的 `old` | 两条写重 → 一条永远轮不到 |
| `generated_from.dev` 已登记 | 漂移提示永远是"未登记"，没人再看 |
| 基线的提交解析得到 | 基线写错 → 落后计数算不出 |
| 基线落后不超过 200 个提交 | 落后过久该有一轮"补规则"（**提示型**，阈值取实测 179 之上） |

## 五、它当场抓到的 1 条失效规则（已修）

`LogFileStore.kt` 的第 3 条规则（"运行时日志的前缀标签"那一段）：

- `old` 是开发期文本；
- `new` 是**第一版**发布态文本（结尾 "…目前没有任何代码反向解析它们。"）；
- 而源码现在是一段**第二版**发布态文本（结尾 "…**日志页的过滤判据就在同一个文件下方
  （[LogFilter]）**，改标签时两侧一起改…"）。

`new` 对不上了 → 该规则被判**失效**。修法：把 `new` 更新到源码现文，
让规则回到"已应用"（幂等）状态。**这是 1 行的最小改动**（不是删规则 ——
规则记录的那次"开发期 → 发布态"变换仍然有意义）。

## 六、判据能不能自己站住（双向自测）

`tools/run_release_rules_guard_tests.sh`（8 条）—— 拿 3 份**就地改坏的真数据**跑，
断言"该红的红、指得出是哪一条、还原后全绿"：

| 桩 | 坏法 | 后果 |
|---|---|---|
| ① | 某条规则的 `old`/`new` 都改成源码里没有的文本 | 规则失效 = 漏清洗 |
| ② | 规则 `path` 指向不存在的文件 | 规则永远空转 |
| ③ | 基线登记 `generated_from.dev` 清空 | 漂移提示永远"未登记" |

---

## 七、明确没做的事

- **没改 release.py 的发布逻辑**：本轮只加判据 + 修 1 条失效规则的 `new`。
  `release.py` 的 `selfcheck_hygiene`、门禁、阻断判定都不动。
- **没把"基线落后"做成阻断**：`release.py` 现有的口径是"纯提示，永不阻断"
  （规则是逐条补的，落后是常态），本轮沿用；守卫里那条 200 阈值也是**提示型**
  （超了该补一轮规则，但不是"这次发不出去"）。
- **没扩到 overlay（`release-overrides/`）**：方案与既有守卫都记着这个通路
  **从未被跑过**（目录不存在，`load_overlay()` 恒返回 `{}`）。本轮不碰。
- **没做真发布验证**：本机不跑 `release.py --to`（要一个发布目标目录与 git 标签），
  结论到"规则三态 + 基线可查"为止。
