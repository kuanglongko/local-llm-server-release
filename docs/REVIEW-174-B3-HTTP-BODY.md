## 一、一句话结论

**API 从 3 个端点长到 7 个之后，服务端没有任何一处核过「发出去的字节是不是合法 JSON」。**

新增一个**会红的**守卫（不是体检表）：`tools/run_http_body_guard.py`，把 `/health`
那份守卫证明过的 Kotlin 词法，从单一端点**扩到全部响应体**。18 条判据 + 12 条自测。

---

## 二、为什么单列这一格

这一格的失效方向与别的模块不同：**两端各自都合法、合起来静默错**。

- 响应体是**手工拼字符串**（Kotlin 原始字符串 + 插值），不是序列化器生成；
- 手拼 JSON 的坏法**全是静默的**：Kotlin 编得过、HTTP 200 照回、没有任何异常或日志，
  只是发出去的字节里多一个引号、少一个逗号 —— 客户端 `JSON.parse` 才抛，
  而现场看起来像「服务随机抽风」或「网络问题」；
- `/health` 已经栽过一次真事故（Issue #77）：`healthJson()` 的行尾引号写多一个，
  拼出来多一对空引号 `""`，整份响应非法；生成接口完全正常，只有依赖 `/health`
  的探活把它判成「服务器不可达」——一个纯粹的误报，病根在服务端。
- 但**那份守卫只覆盖 `/health` 一个端点**。其余 6 个端点、两种 SSE chunk 构造器、
  错误响应，**一条判据都没有**。

`finish_reason` / `n` / 三个协议字段是上一轮才刚补的 —— 也就是说，**功能在长，
而这一格的判据面从来没跟着长过**。

## 三、加了什么（判据清单）

`tools/run_http_body_guard.py`（18 条）—— 每条都对应一个具体坏法：

| 判据 | 防的坏法 |
|---|---|
| 非流式 chat 响应体是合法 JSON | 行尾引号多/少、逗号漏、括号错位（Issue #77 同族） |
| 非流式 completions 响应体是合法 JSON | 同上 |
| chat chunk 构造器是合法 JSON | 单帧非法 —— 客户端在解析那一帧时才崩，看像"流到一半断了" |
| completion chunk 构造器是合法 JSON | 同上 |
| usageJson 响应体是合法 JSON | usage 段拼错，SDK 读不到 token 计数 |
| errJson 响应体是合法 JSON | 错误响应自己非法 —— 报错路径反而更难查 |
| handleAbort 响应体是合法 JSON | 取消端点 |
| 上述各处均不含成对空引号 `""` | 行尾引号写多的**特征症状**（比 JSON 解析更早指到病根） |
| 4 处 choices 都显式带 `index:0` | `n` 只支持 1，index 缺失时 SDK 按 index 定位会错位 |
| Content-Length 取自 UTF-8 字节数（`b.size`） | 按字符数算时，含中文的响应体会被客户端截断/挂起 |
| 至少有一处程序化 JSON 自检兜底 | 与 `/health` 同形的最后一道防线 |

**判据怎么做出来的**：按 Kotlin 词法**真的还原**每一段拼接（复用 `/health` 守卫
证明过的词法：连续引号里**最后 3 个**才是结束符），把插值按**类型正确**的常量代入，
再用真 `json` 模块解析。不是 grep「文件里出现过 JSON」。

词法抽成公共模块 `tools/http_body/kotlin_json_lex.py`：免得每个端点各写一份扫描器，
各错一次。

## 四、判据能不能自己站住（双向自测）

`tools/run_http_body_guard_tests.sh`（12 条）—— 拿 5 份**就地改坏的真源码**跑守卫，
断言"该红的红、指得出是哪一条、还原后全绿"。桩全是**真会写出来的**坏法：

| 桩 | 坏法 | 现实来源 |
|---|---|---|
| ① | chat 响应体行尾**引号多一个** | Issue #77 真事故同款 |
| ② | completions 响应体**漏一个逗号** | 手拼 JSON 的经典错误 |
| ③ | chat chunk 的 `choices[0]` **删掉 `index`** | SDK 按 index 定位时错位 |
| ④ | `Content-Length` 改用**字符数** | 含中文的响应体被截断 |
| ⑤ | `errJson` **漏右花括号** | 报错路径自己非法 |

**为什么必须有这份自测**：本守卫是词法的，两个自欺方向都不报错 ——
- 判宽了恒绿：最容易的是「插值一律填 0」，会把字符串位的**引号结构错填平**
  （开发这一版**第一遍就真踩到**：把 `"id":"$id"` 的 `$id` 也填成带引号的 `"m"`，
  还原出 `"id":""m""`，反而假红）；
- 判窄了恒红：pattern 差一个字符 → 守卫永远 FAIL → 有人 `|| true` 掉。

只对着真源码跑一次看它绿，这两件事都发现不了。

## 五、明确没做的事

- **没动业务逻辑**：这一轮只加判据，`HttpApi.kt` 一个字节没改（本轮 diff 里它不在）。
- **没给每个端点都加运行时自检**：那要动业务代码（加 `JSONObject` 调用），
  超出「只加判据」的范围。当前**唯一**的程序化兜底仍是 `/health` 的 `JSONObject` 自检
  （判据第 11 条钉住它还在）；其余端点的兜底是**离线守卫**这一层。
  这条边界值得记下：**离线守卫锚的是"源码形状"，不是"运行时发出的字节"** ——
  运行期真正的字节校验仍是一处空白（与本仓库「锚结构关系、不锚存在性」的纪律一致，
  但读者该知道它没被覆盖）。
- **没做真机验证**：本机无 Android 设备；结论到「源码词法还原 + 宿主真解析」为止。
