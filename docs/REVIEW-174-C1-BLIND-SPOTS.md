## 二、为什么单列这一格

这两处的坏法都是**零症状**的：

- **`cpu_feat.c`** 是**唯一**决定"加载哪个 rnllama 变体"的地方。位常量写错一位、
  或 `AT_HWCAP` / `AT_HWCAP2` 的来源写反，结果都是"探测某一位恒 0/恒 1"——
  App 照常启动、照常推理，只是**静默选到慢变体**（或在不支持的机上选到会 SIGILL 的
  快变体）。没有异常、没有日志，只有"这台机器怎么这么慢"这种说不清的体感。
- **`StderrPump.kt`** 把 native stderr 接进日志管线。native 崩溃前最关键那句
  （`ggml_abort: ...`）只写 fd 2，接不上就**看不到**；而接法错了更坏：读端一旦
  停止排空，pipe 缓冲写满后 native 线程会**永久阻塞在 `write(2)`** ——
  卡死比崩溃更难查（现场没有崩溃记录，只是"卡住了"）。

## 三、加了什么（判据清单）

`tools/run_cpu_feat_guard.sh`（20 条）：

| 判据 | 防的坏法 |
|---|---|
| 真源位常量是 bit 20 / bit 13（uapi 值） | 常量写错 → 某位恒 0/恒 1，静默选错变体 |
| 单测里的常量与真源**同值** | 两边**一起改错**时"比对"失效（只判真源会假绿） |
| dotprod 取自 `AT_HWCAP`（h1） | 来源写反 → 一位恒 0 |
| i8mm 取自 `AT_HWCAP2`（h2） | 同上 |
| 两次 `getauxval` 分别读两个来源 | 全读同一个 → 高位探测全废 |
| native 返回 4 个槽 / Kotlin 按 `c[0]`、`c[1]` 分工 | 槽位对调 → 判据整个反过来，两边都"看起来对" |
| raw 两槽被回填 | 日志取错槽 → 印出错的位数 |
| StderrPump 幂等闸 / 只动 fd 2 | 重复 start 重复改 fd；动了 stdout 会污染子进程 |
| **sink 调用被 `runCatching` 包住** | sink 抛异常即停排空 → pipe 写满 → native 阻塞 |
| 整段 `start` 被 `runCatching` 包住 / 失败复位 | 失败后不能重试 / 影响推理 |
| read 失败即 break / 超长残留也冲刷 | 在 `-1` 上空转 / 崩溃写一半不留死缓存 |
| **宿主侧行为单测**（编译 + 运行） | 合成 hwcap 覆盖四种组合，断言槽位与取值 |

**行为单测怎么在 x86 宿主上测 ARM64 库**：不调 `getauxval`，而是把
"位 → 输出槽"那套判据单独编出来跑，用显式的合成 hwcap 值覆盖 `00/10/01/11`
与"来源写反"两个反例。这样 CI 的 x86 宿主也能拦住常量回归。

## 四、判据能不能自己站住（双向自测）

`tools/run_cpu_feat_guard_tests.sh`（10 条）—— 拿 4 份**就地改坏的真源码**跑，
断言"该红的红、指得出是哪一条、还原后全绿"：

| 桩 | 坏法 | 后果 |
|---|---|---|
| ① | i8mm 位常量写错（`1<<13` → `1<<12`） | 探测恒 0，静默选慢变体 |
| ② | dotprod 来源写反（读 `AT_HWCAP2`） | 一位恒 0 |
| ③ | Kotlin 侧槽位对调（`c[1]` 当 dotprod） | 判据整个反过来 |
| ④ | `sink` 裸调（不包 `runCatching`） | sink 抛异常即停排空 → native 卡死 |

## 五、明确没做的事

- **没动被审源码**：`cpu_feat.c` / `StderrPump.kt` / `LlmEngine.kt` 一个字节没改
  （本轮是**纯加判据**；三处核下来当前都正确）。
- **行为单测没真跑真机 `getauxval`**：宿主是 x86，`AT_HWCAP2` 的语义与 ARM64 不同；
  本测试覆盖的是**常量与槽位判据**，不是"内核报告了什么位"。
  真机那一层由日志里的 `hwcap=0x... hwcap2=0x...`（`describe()` 打的原始读数）兜底。
- **没给 `StderrPump` 做 I/O 层的行为测试**：`Os.pipe` / `dup2` 需要真实 fd，
  宿主上要用 stub 才能跑，而那会引入一份"与真 `Os` 语义可能有差"的假实现；
  本轮只钉**结构判据**（排空与异常隔离的写法）。这条边界如实登记。
- **方案里的"守卫弱"两级（`LogExport.kt`、`MainActivity.kt`）本轮未动**：
  它们不是"零覆盖"，是"覆盖偏弱"，属下一轮。
