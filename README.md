# Local LLM Server（小万本地推理）

Android 手机上**完全离线**的 GGUF 大模型推理 App：在应用进程内用 llama.cpp 跑推理，
一边提供图形界面聊天，一边对局域网提供 OpenAI 兼容 HTTP 接口。模型与对话记录只留在本机。

包名 `com.xiaowan.localinference` · 最低 Android 8.0（API 26）· 仅 `arm64-v8a`

## 能做什么

- **图形界面**：模型库（列表/别名/卸载）、多会话聊天（气泡 + 单条删除 + 重新生成 + **导入/导出** + **角色卡**）、参数区、本地服务开关与**存活探测**、日志（**标签多选 + 任意关键字筛选**）与导出
- **HTTP 接口**：`/health`、`/v1/models`、`/v1/models/{id}`、`/v1/chat/completions`（支持 `stream`、`tools`）、`/v1/completions`、`/v1/abort`；`GET /` 是**自带测试页**（同源内嵌 HTML，浏览器直接打开就能聊）
- **结构化输出**：`response_format` 的 `json_object` / `json_schema`，走 GBNF grammar 在生成循环里逐 token 约束
- **KV 前缀复用（prompt cache）**：多轮对话与带 `tools` 的固定段不再每轮从零 prefill，只算新增的尾巴
- **嵌入（embedding）模型：双常驻**：可与对话模型**同时**加载（各持一份独立 Session），为 RAG 提供逐条文本向量（归一化后、按模型声明的池化方式取值）
- **知识库（RAG）**：文档分块 → 逐块编码 → 落 `filesDir/rag/<库名>/`（**索引 + 正文**），**自带指纹**（模型路径/大小/mtime/维度/切块参数/**正文 hash**，任一变化即作废重建），重启不丢；独立的「知识库」页可点库**回填正文**编辑、「保存正文」只写正文（毫秒级）、「建索引/重建索引」重算向量、「追加」只编码这一条、「导出库 / 导入库」走独立信封（**一个向量都不带**）；App 内聊天与远端 HTTP 各有独立开关与库名
- **可调参数**：`n_ctx`、线程数、`parallel`（**当前不产生并发**）、`batch/ubatch`、采样与惩罚参数、Flash Attention、KV cache 量化、权重重排（`repack`）、mmap 开关、默认关闭思考
- **可恢复**：设置页底部「还原默认设置」一次性恢复整页参数（含端口 8080 与局域网开关），**点下去之前先弹确认框**
- **推理后端**：CPU（按指令集选 4 个预编译变体）+ OpenCL GPU + Hexagon NPU（HTP，实验性，默认关闭）
- **可取证**：Java 异常落 `crash_last.txt`；native stderr 实时并入会话日志；可选「崩溃取证模式」把 native 全量日志与信号现场不经 JVM 直写文件
- Kotlin 侧**零第三方运行时依赖**（只用 Android framework 与 `org.json`），无账号、无遥测

## 快速开始

1. 安装 APK（Releases 提供 debug 构建；本仓库不含模型权重）。设置页顶部会显示当前构建的版本号与构建号，报障时直接引用它。
2. 把 `.gguf` 放进 `Android/data/com.xiaowan.localinference/files/models/`，在 App 里选中 → **加载**。该目录属应用私有外部目录，**不需要授予存储权限**。
3. 要用推理参数以外的默认值，在「设置」里调；参数**以 App 为准**，会覆盖请求里的同名字段。
4. 给别的设备用：打开「局域网访问」（否则只绑 `127.0.0.1`），记下端口与通知里显示的 IP。
5. （可选）要限制"谁能调生成端点"：设置页「本地服务」分组里的「接口鉴权」一栏点「生成 token」，「复制」后填进客户端（第三方 UI 填它的「API Key」框即可）。不改这一步就是默认不开鉴权。

```bash
curl -s http://<手机IP>:<端口>/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{"model":"qwen2.5-1.5b-instruct-q4_k_m",
       "messages":[{"role":"user","content":"用一句话解释 KV cache"}],"stream":true}'
```

## HTTP 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/` | **自带测试页**（同源，内嵌 HTML，零外部依赖）：浏览器直接打开即可探测 `/health`、看模型列表、流式多轮聊天，带折叠设置区 |
| OPTIONS | 任意路径 | CORS 预检，统一回 `204`，见「浏览器 / CORS」 |
| GET | `/health` | 存活探测（App 内「存活探测」按钮即真发此请求）；含 KV 复用与后台冻结痕迹字段 |
| GET | `/v1/models` | 全库模型列表；主 id 用**别名**（Ollama 风格短名），文件名在 aliases 里 |
| GET | `/v1/models/{id}` | 单个模型（OpenAI 兼容）：id 就是列表里那个**别名**（URL 编码后传，中文别名也行）；当前加载的那一个带 `profile` 档案 |
| POST | `/v1/chat/completions` | 对话补全，认 `messages`（含 `system`）、`stream`、`tools`、`stop`、`response_format` |
| POST | `/v1/completions` | 文本补全，认 `prompt`、`stop`、`response_format` |
| POST | `/v1/abort` | 取消当前生成（无 body、无参数） |

采样参数由请求体给出，缺省时用与 App 内参数区一致的一组默认值
（`temperature=0.8`、`top_p=0.95`、`min_p=0`、`top_k=0`、`repeat_penalty=1`、
`repeat_last_n=64`、`frequency_penalty=0`、`presence_penalty=0`、`max_tokens=512`），
也认 OpenAI 的 `seed`。显式给出的取值必须落在合法范围内，否则返回 `400` 并说明原因。
线程、上下文、`batch/ubatch`、KV cache 等**加载期**参数仍在 App 里定，接口不认。

**超限请求"拒绝"而不是"截断"**：请求体上限 4 MiB（超限 `413`）、请求行与单个头行上限
8192 字节（超限 `400`）。

**并发形态：单并发**，第二个请求直接 `503`、不排队（生成循环持引擎锁，App 内聊天占用时同理）。
设置页 `parallelN` **不改变这一点** —— 它只是把 `n_seq_max` 传给库，服务端没有多 slot 调度，
反而会按份数瓜分 `n_ctx`（`parallelN=2` + `n_ctx=4096` → 每路实际可用约 2048），**建议保持 1**。
真正的多 slot 调度评估后**已搁置**：手机端是单用户场景，收益与改动量不成比例。

**「服务在跑」与「用户想要服务在跑」是两个不同的标志**：`isRunning` 报实际状态（端口能不能连上），
`isDesiredRunning` 报用户意图。看门狗自愈只看后者。

### 鉴权（可选，默认不开）

在设置页「本地服务」分组里的「接口鉴权」一栏生成一个 token 之后，
只有**生成端点**（`/v1/chat/completions`、`/v1/completions`、`/v1/abort`）
要求 `Authorization: Bearer <token>`：

```bash
curl -s http://<手机IP>:<端口>/v1/chat/completions \
  -H 'Authorization: Bearer <token>' \
  -H 'Content-Type: application/json' \
  -d '{"messages":[{"role":"user","content":"你好"}]}'
```

不带 token / 带错 token 一律 `401`（错误正文说明是「没带」还是「不匹配」，但绝不回显 token）。

以下路径**一律免鉴权**：`OPTIONS`（浏览器自动发预检，拦了等于 CORS 白做）、`GET /health`
（存活探针与自己人打的都是它）、`GET /v1/models` 与 `GET /v1/models/{id}`（只读的清单与单查，
第三方 UI 的模型下拉框靠它填充）、
`GET /`（在地址栏里打开，没地方填 header）。路径匹配是"落在之下"而不是"以此开头"：
`/healthz`、`/v1/models-evil` **不会**被当成豁免路径；除这两条精确豁免外，其余 `/v1/*`
（含未知路径）一律要凭据。

**它不是访问控制**：token 只挡住没带凭据的调用方，挡不住同网段能直连的设备（token 走明文 HTTP，
威胁模型是"可信局域网"）。**默认不开**，不改这一步行为与升级前完全一致。

### 停止序列（`stop` / `stop_sequences`）

两个端点都认 OpenAI 的 `stop`（字符串或数组）与别名 `stop_sequences`，两个字段都给时**取并集**。
命中后停止序列本身不会出现在响应里（与 OpenAI 一致）。拦截在生成循环里逐 token 判，
所以 `stream=true` 时也不会把越界内容先发出去，并正确处理「stop 串跨多个 token」。
取值**语义错**才 `400`（如**空串**）；"条数多""单条太长"属于性能边界，只截断 + 落日志。

```bash
curl -s http://<手机IP>:<端口>/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{"messages":[{"role":"user","content":"只输出一句话，然后写 END"}],
       "stop":["END"],"stream":true}'
```

### 协议字段：`max_completion_tokens` / `logit_bias` / `logprobs`

两个端点都认这三个 OpenAI 字段。它们此前**完全没被读**，是被静默忽略的 ——
客户端以为自己设了值、服务端照 `200` 回、输出却按默认值走。

- **`max_completion_tokens`** —— 新版 OpenAI SDK 的默认字段名。它与 `max_tokens` 是**同一个量**：
  两者共用同一份上限判据（`1..8192`）与同一句 `400` 文案；**两个都给且取值不同**时直接 `400`。
- **`logit_bias`** —— `{"<token_id>": <偏置>}`，id 必须是十进制整数（`"1.5"` / `"abc"` /
  `" 12"` / `"+12"` / `"-12"` 全拦），取值必须落在闭区间 `[-100, 100]`。
  词表里没有的 id 在采样器里是**空操作**，所以不做词表校验。条数超过 `300` 条**只截断 + 落日志，不 `400`**。
- **`logprobs` / `top_logprobs`** —— 两者是**绑定**关系：`top_logprobs` 单独给是协议错误
  （OpenAI 自己也 `400`）。⚠ 本轮只补齐协议面，不产出数据：客户端要 `logprobs` 时响应里会出现
  `"logprobs":null`（而非 `[]`/`{}`），日志里另有一行说明。

三个字段一个都不给时，请求行为与引入本特性之前**逐字节相同**。

```bash
curl -s http://<手机IP>:<端口>/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{"max_completion_tokens":64,
       "logit_bias":{"12":-100,"34":5},
       "logprobs":true,"top_logprobs":3,
       "messages":[{"role":"user","content":"用一句话解释 KV cache"}]}'
```

### `finish_reason`

两处响应（chat 与 completions、流式与非流式）统一给出四档，优先级写在纯函数 `FinishReason.of` 里：

| 优先级 | 取值 | 何时 |
|---|---|---|
| 1 | `cancelled` | 客户端断连 / `/v1/abort` |
| 2 | `length` | 跑满 `max_tokens` |
| 3 | `tool_calls` | 解析出了工具调用 |
| 4 | `stop` | 模型自己收尾（EOS）或命中 `stop` 序列 |

`length` 与 `stop` 必须分开：SDK 按 `finish_reason == "length"` 决定要不要续写/重试，
报成 `stop` 时**半截输出会被当成完整回答**存库、缓存、丢弃。
「被取消且正好跑满」取 `cancelled`：取消是**外部意图**，跑满只是顺带够到上限。

### `n`：只支持 1，其余明确 `400`

本服务一轮请求只生成一条序列（`parallelN` 是**引擎级**配置，不是请求级参数），所以 `n` 只接受缺省或 1：

- `n` 缺省 / `n: 1` → 正常；
- `n: 2` 及以上 → `400`，文案写明"只支持 1"，**不静默截成一条**；
- `n: 0` / `n: -1` / `n: 1.5` / `n: "abc"` → `400`，报的是**取值写错**而不是"不支持"。

### 请求取消（客户端断连 / `POST /v1/abort`）

客户端中途放弃时，服务端**立刻停**，不再白跑满 `max_tokens`。三条路径（流式断连、
非流式写响应时抛异常、显式 `/v1/abort`）都收敛到「当前正在生成的那一轮」：

```bash
curl -s http://<手机IP>:<端口>/v1/abort -X POST
# -> {"aborted":true,"generating":true}   真的停到了某一轮
# -> {"aborted":false,"generating":false} 当时没有轮次在跑（不是失败）
```

- `aborted` 区分「停到了」与「本来就没有」，两者都返回 `200`（取消不该因竞态而失败）。
- 取消**带归属**：只有「当前轮次」的取消才生效。
- 停止后 `finish_reason` 报 `cancelled`，不退化成 `stop`。
- **「停止」是对这一轮说的，不是对整个进程说的**：一轮结束即复位。

### 后台保活：被冻住时会发生什么、客户端该怎么接

部分国产 ROM 会在切后台后**冻结**这个进程（cgroup freezer）。冻结期间：
端口仍在 `LISTEN`、TCP 握手照样完成，但**没人 accept** —— 调用方看到的是"发出去的请求一直挂着"，
切回前台就恢复。

**边界**：内核的冻结判据只看 `MemFree` / `SwapFree`，与"是不是前台服务""有没有无障碍权限"**无关**。
应用侧做不到"永不被冻"，能做的是把"卡死"降级成"明确失败 + 快速恢复"。服务端这边做了四件事：

| 动作 | 效果 |
|---|---|
| 空闲期自连探活 5s 一次（生成期退到 30s） | 解冻后 **1~5s** 恢复受理 |
| **生成期不探活、不重启** | 绝不掐断那条正在续传的流 |
| 探活失败只登记 `restart_pending`，**等空闲才重启** | 避开"监听假活"与"有流在跑"同形的歧义 |
| 连接受理后 **5s** 内收不到完整请求头 → 回**可读的 503** | "连上但不说话"从静默断连变成明确失败 |

`/health` 新增四个字段，把"冻过没有"变成可归因：

```bash
curl -s http://<手机IP>:<端口>/health
# -> ...,"frozen_ms":63000,"frozen_count":3,"frozen_total_ms":185000,"restart_pending":false
```

- `frozen_ms`：最近一次"看门狗该醒却晚了"的超出量（毫秒，`0` = 没检出过）；
- `frozen_count` / `frozen_total_ms`：累计次数与累计毫秒；
- `restart_pending`：是否**欠着**一次"空闲后重启"。

**客户端侧**（这半边只能客户端自己做）：

```
首次连接超时：5~10s（解冻后的第一拍会慢）
读超时（流式）：30~60s（服务端每 ≤800ms 发一帧 `: ping` 心跳）
重试策略：指数退避 1s / 2s / 4s / 8s …，上限 30s，可无限重试
```

- **别把 `connect` 成功当服务健康** —— 冻结中的进程 TCP 层照样握手，但没人 accept。
  判据只能是"收到第一个字节"，或先打一次带超时的 `GET /health`。
- 流式断了（EOF / RST）**一律当"没完成"**，不要落库；用同一份 `messages` 重发整轮即可
  （prompt cache 能命中前缀）。判据只有 `finish_reason` 或 `[DONE]`。
- 优先用「忽略电池优化」提高存活率，而不是长期 `PARTIAL_WAKE_LOCK`。

**设置页「后台保活」一节**给出三行读数，把"权限到底开没开"从猜变成可读：

```
无障碍服务：已开启 / 未开启 / 查不到        ← 读系统的 ENABLED_ACCESSIBILITY_SERVICES
忽略电池优化：已开启 / 未开启 / 查不到      ← 读 PowerManager
冻结痕迹：上次 63s，累计 3 次 / 185s      ← 取自最后一次「存活探测」的 /health
```

- **三项都读系统真值**，不读本应用的标志位；**"查不到"与"未开启"分开报**。
- 三个按钮分别是「开无障碍」「免电池优化」「应用详情（自启动 / 省电策略）」。**从系统设置改完回到 App 会自动重读**。
- 那个无障碍服务**不做任何辅助功能**：不订阅界面事件、不读取窗口内容，唯一用途是让部分 OEM
  提高本进程存活优先级 —— **效果因 ROM 而异，不做承诺**。
  ⚠ 应用商店通常不接受无障碍权限（本项目只做侧载分发，不受此限）。

**服务自身的前台服务类型声明了 `dataSync|specialUse`**：`dataSync` 描述"进程在做数据传输 /
本地文件处理"（事实成立），`specialUse` 是 API 34+ 的兜底类型。这样将来若抬 `targetSdk`，
服务**不会**吃 Android 15 给 `dataSync` 定的 6 小时 / 24 小时**时间额度**。

⚠ 这条**换不到**冻结豁免（冻结判据只看内存），也不改进程优先级：

- `oom_score_adj` 由"进程是不是前台服务"决定，与 FGS 的**类型位**无关 —— 多声明一个类型不会让它更低；
- 冻结判据只看 `MemFree` / `SwapFree`（见本节开头），与前台服务类型同样无关。

所以收益是**语义完备**（声明与实际用途对齐、不吃将来的时间额度），**不是**"不再被冻"。

### KV 前缀复用（prompt cache）

多轮对话**协议上无状态**：每轮都要重发整段历史。本版做了前缀复用 ——
本轮 prompt 与上一轮进过 KV 的 token 序列共享前缀时，直接留用那段 KV，只 prefill 新增的尾巴。
复用是纯加速，协议上看不出来，只能靠 `/health` 的字段读：`kv_cache_valid`、`kv_reuse_tokens`、
`kv_prefill_tokens`、`kv_rounds`，以及 `kv_lcp_tokens`（上一轮的**公共前缀** token 数）。

```bash
# 第 2 轮：接着问，历史全部命中
curl -s http://<手机IP>:<端口>/health
# -> "kv_cache_valid":true,"kv_reuse_tokens":<上一轮全部>,"kv_prefill_tokens":<只剩新增那几句>,
#    "kv_rounds":2,"kv_lcp_tokens":<公共前缀>=上一轮全部
```

复用的判据保守到刻意：逐 token 比前缀、只能复用开头那一段、不足 16 token 不复用、
账本无效（换模型 / 卸载 / 取消 / 上一轮出错 / prompt 超长）一律不复用。

**`kv_lcp_tokens` 是把「没命中」拆开的那把刀**：`kv_lcp_tokens` **很大**却仍 `reuse=0`，
是门槛/容量拦下的（prompt 已达 `n_ctx`，或 `total-1 < 16`），属于"差一点"；
**很小**则说明两轮 prompt **真的不一样** —— 例如检索块曾经拼在 system 段（每轮都变，
分叉点落在最前面）。App 日志里未命中那行会写
`KV 前缀复用：未命中（公共前缀 N tok / 门槛 16），全量 prefill M tok`。

App 设置页有「丢弃 prompt 缓存」按钮：换了 system 提示词之后旧前缀本来就匹配不上，
但那几 MB KV 会一直占着显存。

### 嵌入模型（`embedding`，双常驻）

可以**同时**加载一个对话模型和一个嵌入模型 —— 这是"双常驻"：两份模型各持一份
独立 Session，互不影响。加载/卸载嵌入模型**不会**碰对话模型，反之亦然
（卸载日志带角色：`卸载[对话]` / `卸载[嵌入]`）。

嵌入模型走**同一套模型库机制**（`models/*.gguf` 目录 + 别名），在设置页单独指定一个。
**BGE 系**（`bge-small-zh-v1.5` / `bge-large-zh-v1.5`）与 **nomic**、**Qwen3-Embedding**
这类句向量模型都可用。加载后日志会出一行

```
embed model ready: <desc>, n_ctx=..., n_ctx_seq=..., seq_max=..., n_embd=...,
                   n_embd_out=..., pooling=..., n_batch=..., n_ubatch=..., full_rows_fit=...
```

**`n_batch` 与 `n_ubatch` 是两个独立的门**：因果模型（Qwen3-Embedding → `llama_decode`）
走 `n_batch`；非因果模型（BERT 系 bge → `llama_encode`）走 `n_ubatch`。两者都由本仓库
显式设成 4096（旧版不传 = 用库默认值 2048 / 512，8 条满长一次就顶出容量）。

⚠ 设置页那格「每批编几条」拧的**不是**这两扇门，而是"一次收几条"。
`full_rows_fit` 报的是"最多一次编几条满长"，由 `n_ctx_seq - 1` 与两道门除出来；
它若小于批大小那格，满长的那几批会被切段（安全，但多一两次 decode），日志里另有预警。

**嵌入 ctx 那一格**：设置页的「嵌入每批上下文（每条文本）」默认 512、上限 4096，它就是
"内存占用为啥高"的那一格 —— KV / output / compute buffer **都按「它 × 8」分配**，
而**批大小那格不影响内存**（它只决定"一次塞几条"）。native 侧加载时报一行
`[embed内存] …估算 KV≈… MB + output≈… MB ｜ 进程 RSS … MB（含模型 mmap，别当增量读）`。

**`n_embd` 与 `n_embd_out` 必须相等**（库按 `n_embd_out` 分配 output buffer，读向量按
`n_embd` 步长走）；`pooling` 是模型在 GGUF 里声明的池化方式。向量从 `embd_seq` 还是
`embd.data` 读，由池化档决定（`MEAN`/`CLS`/`LAST` 走 `llama_get_embeddings_seq`，
只有 `NONE` 走 `llama_get_embeddings_ith`）。

**算一个向量**（服务端内部接口，HTTP 侧见 `/v1/embeddings`）：输入一条文本 → 输出
**已 L2 归一化**的向量（维度 = `n_embd`）；池化按模型声明的方式取值，`RANK`（rerank 模型）
**拒绝**；空文本 / 归一化失败（零范数 / NaN）返回"这条没有可用向量"，**不编造方向**。

**几个刻意选择的档位（都与"省内存"有关）：**

| 档位 | 值 | 为什么 |
|---|---|---|
| `embeddings` | **强制 true** | 不设时取到 null，表现为**静默返回零向量**（检索全空而接口 200） |
| `n_ctx` | **默认 512，上限 4096** | 嵌入不做自回归，KV 是纯冗余，但库仍按 `n_ctx` 分配 output buffer |
| 超长文本 | **截断到 `n_ctx-1`** | 让整次检索失败比"用前 N 个 token 的语义"更糟。截断有日志可辨 |
| 每条前清 KV | **必做** | 嵌入是无状态逐条前向，复用上一条的 KV 会让向量混进上一条的语义 |
| 与生成并行 | **独立锁**（`embedLock`） | 检索**不用等**一整轮生成 —— 这正是双常驻要买的东西 |

**注意「双常驻 ≠ 免加载」**：持久化解决的是**索引**（向量落盘，重启不用重算），
**模型**仍会随进程被杀而归零 —— 第一次使用仍要加载。

### 知识库索引与持久化

索引存在 `filesDir/rag/<库名>/index.bin`，**正文**存在同一个目录的 `texts.jsonl`
（一行一条 JSON，行序 == 索引行序）。另有 `meta.json`（**只为人看**：建库时间、模型、切块参数）。

**索引自带指纹，任一变化即作废重建**：嵌入模型路径 / 大小 / mtime、向量维度、切块参数、
正文 hash、正文行数、池化方式、`n_embd_out`、**批大小**、格式版本。指纹不匹配 = **当作没有索引**
（重建），绝不"凑合着用"：错位的向量会让余弦量纲直接对不上，排序看起来像随机，而接口 200、日志干净。

**失效时要说得出是哪一项**：日志给出具体字段与两边的值
（`[知识库] 索引不可用（"tes1"）：池化方式对不上：索引 q=3 ≠ 当前 q=2（字段 q）`），
而不是把十几个字段压成一句"模型或参数变了"。

**四态，不是两态**（`none` / `empty` / **`partial`** / `valid`）：

- `none` —— 文件不存在 / 指纹不符 / 损坏 → **必须重建**；
- `empty` —— 索引有效但**没有任何条目** → **不必重建**；
- **`partial`** —— **半份索引**：指纹与当前配置**完全一致**，向量只到第 `count` 行为止。
  它**不能检索**，但它是**可续**的；
- `valid` —— 有可用索引。

把 `empty`/`none` 混成一个 `null` 会出一个真实故障：每次打开空知识库都触发一次"重建"，
而重建结果还是空 —— 用户看到页面一直在转，没有任何日志说清它在转什么。

**建索引断了不再从头跑**：`savePartial` 留下的那半份索引，指纹用的是**完整正文**的，
所以判据只剩一条：**指纹同源 + 前缀连续**。续编不重放块，只"跳过前 `count` 块、接着编"。
指纹里任一项与落盘那次不一致时整档作废**从头**，且**说出来**（否则"我明明点的续跑，
它又跑了两小时"，日志里没有一行指向原因）。定期落盘每 **2000 块**（叠加"至少每 3 分钟"）
落一次盘，**只在没有失败时落**（有失败时向量不能往前挤，挤了就是整体错位）。
进度落盘交出去的那份正文必须是**这份库的全部块** —— `saveProgress` 一处收口拼接，
调用方只报"编完了几块"。

**几处刻意的安全选择：**

| 选择 | 为什么 |
|---|---|
| **原子落盘**（写 `.tmp` 再 `renameTo`） | 写到一半被杀会留下半截文件；`renameTo` 原子，读到的一定是"完整的" |
| **库名净化，非法即拒**（不是"替换掉就放行"） | `../` 会让索引落到库目录之外 —— 那是任意路径写入 |
| **任何损坏 / 截断都整体拒绝** | 部分可信的头比没有头更危险：调用方会按错的 `dim`/`count` 读向量 |
| **显式小端** | 不指定字节序时 float 在别的大端环境里读成乱码，**不崩**，只是检索全错 |
| **建库前确认嵌入模型在位** | 没加载时 `embed()` 逐条返回 null → 整库向量全空，而"建库成功"照样返回 |
| **低分一条都不注入** | 没有命中时正确行为是"不注入"，硬塞最不像的几条会用无关段落**污染**回答 |
| **同分按下标小的优先** | 让同一次查询在同一份数据上永远返回同一顺序 |

分块的三条硬约束：**绝不切在 UTF-8 码点中间**（切在 continuation 字节上那一段永远编码失败）；
**块与块无缝覆盖**（否则中间几个字节的正文永远进不了索引）；**相邻块保留重叠**。
另有块数上限 `maxChunks`（默认 **16384**），撞上限时**超出部分不进索引**，且**一定有日志**。

**两条"切得不好"的日志，分别管两种事**：**硬截**（块边界不好，内容全在，只是切得糙 ——
召回率低）与**截断**（块没了，内容真的少了一截）。两者后果差一个量级，所以**分开报**。

**建库前会先说一句"要多久"**：条数 ≥ 200 时弹一次确认，写明量级（"约 1~4 分钟"，
上万条会说"数小时级"）与"期间这一屏不能操作"；导入确认框里也带同一句。
条数小于阈值**不打扰**。**提示报小了比不提示更坏**，所以量级按 **0.10~1.00 秒/条**（区间，不是精确值）。

建库耗时是**逐条前向**堆出来的，所以线程数直接乘在里面：嵌入线程数与本机核数绑定
（`LlmEngine.defaultThreads`）。**合批**也已落地：一次前向编**默认 8 条**
（设置页「每批编几条（1=关合批）」，上限由 native 的 `n_seq_max` 定），
条目之间靠 `llama_batch` 的 `seq_id` 隔离，每条的 `pos` 从 0 起。
- **所有档都合批**。库自己池化的三档（`MEAN` / `CLS` / `LAST(3)`）
  的向量取自 `embd_seq` —— 那份 buffer 在多 seq 下**每个 seq 一行**，第 j 条读
  `llama_get_embeddings_seq(ctx, j)`，与单条路径（实参写死 0）是**同一个 API**。

  ⚠ 这一条**换过方向**，值得记下为什么：早期它只放行 `NONE` / `UNSPECIFIED`，
  理由是"库自己池化的档（MEAN/CLS/LAST）向量取自 `embd_seq`，那份 buffer 在多 seq 下的
  布局**没验过**"。那是当时的诚实，代价正是上面那两个模型**一条都合批不上**
  （只拿到线程数那一半）。后来把它验了：`embd_seq` 在多 seq 下
  就是每个 seq 一行。于是闸撤了。

- **改批大小必须重建索引**：那一格进了指纹（`g`）。不同批大小下每条的位置预算**可以不同**，
  不进指纹 = 改了它、旧索引仍被当成"仍然可用"，而新旧向量一旦不逐位相同，检索就是
  "用一种语义命中、注入另一种语义的正文"。它是**必填**字段：旧格式指纹里没有它 = 认不出来 = 重建一次。

**合批的读数是必须的**：建库结束时打一句
`[知识库] 批级读数（本段批大小=N，只算这一次建库）：合批 X/Y 条（Z%，B 批，共 M ms）`，
⚠ 报的是**本段增量**而不是进程级累计；`/health` 另有 6 个累计字段
（`embed_batch_batches` / `embed_batch_entries` / `embed_batch_fallback_batches` /
`embed_batch_fallback_entries` / `embed_batch_ms` / `embed_batch_size`），以及
`embed_batch_size_index`（**建当前库的索引时用的**那个批大小）。

**编码失败时一定会被报出来**，且带"是哪一条、为什么"：

```
[知识库] lib 索引已生成但**待重建**：成功 97 / 失败 3 条（切块 100，正文 100 行已保留），dim=384
[知识库] 失败明细：#12 向量范数为 0（零向量/下溢）—— 池化方式可能与该模型不符；#45 …
```

失败的三条明确语义：**正文留下、向量缺席、整库标记需重建**。向量只保留**与正文行号一一对应的前缀**
（中间失败时后面成功的向量**不能往前挤**）。失败原因**带实值**（范数 / token 数 / 维度 / 池化类型）。

  ⚠ 这里有一处**还没有真机读数**，要如实说：把"合批"扩到所有档之后，
  还没有在设备上做过"同一条文本、合批跑 vs 逐条跑、两个向量逐位比"这件事。
  离线判据只能证明"切分对、指纹对、接线对、读写对"，**证明不了真机上算得准、够快**
  （本环境**无 NDK / 无设备 / 无嵌入模型**）。调试页的「批大小一致性检查」就是这件事的入口。

**离线判据**：`run_embed_text_tests.sh`（归一化 / 池化计划 / 向量从哪一路读）、
`run_dual_model_guard.sh`（真两份 Session 隔离）、`run_embed_failure_guard.sh`（失败可归因）、
`run_rag_index_tests.sh` / `run_rag_index_store_tests.sh` / `run_rag_index_guard.sh`（分块 / 指纹 /
持久化 / 接线）、`run_embed_seq_guard.sh`（多 seq 下池化向量取自哪一行
  （ISSUE #269 第 3 步）。早先库自己池化的三档不合批（理由是 `embd_seq`
  的多 seq 布局没验过）；撤闸后新增的唯一风险就是"读第几行"，而它的失效形态全静默）、
`run_embed_batch_guard.sh`（合批从头到尾口径与逐条逐项相同）、
`run_embed_batch_tuning_guard.sh` / `run_embed_stats_tests.sh`（读数与批大小可调）、
`run_embed_parity_guard.sh` + `run_embed_parity_tests.sh` 与
`run_embed_retrieve_guard.sh` + `run_embed_retrieve_tests.sh`（调试页「批大小一致性检查」：
逐条与合批两条路**逐位**比对向量，并按两种批大小各编一套向量比"命中的行下标"）。

### 知识库问答（App 内检索注入）

在独立的「知识库」页配置一个知识库后，**App 内聊天**会自动把检索到的相关片段拼在
**最后一条 user 消息的正文之前**（块在前、提问在后）。开关、库名、建库入口都在该页。

- **开关默认开**（App 内）：这一屏的人知道自己配了知识库，默认不勾的后果是"配好了但从来没用上"。
- **建索引**：填库名 + 把要索引的文本**一行一条**粘进文本框，点「建索引/重建索引」。
- **注入位置**：拼在最后一条 user 之前，**不动 system 段**。两件事决定了它必须在这里：
  **KV 前缀复用**（system 在 prompt 最前面，注入块每轮都变，放 system 段等于把分叉点拉到 pos 0）
  与**语义归属**（检索是本轮提问的附加信息）。拼进 user 正文而不是另插一条 user 消息：
  后者会让严格交替角色的模板串味或报错。
- **每轮重算**：检索结果不落盘、不进 `SessionStore`。
- **查询用最后一条 user 消息**：用整段历史当查询会把前几轮的话题也平均进来，命中率反而下降。

**没有命中时的行为**：**不注入**，而不是"把最不像的几条硬塞进 prompt"。
阈值（默认 `0.35`）以下的一条都不要。

**「没注入」有三种成因，日志给三句不同的话**（旧版压成同一句，而处置**相反**）：

| 日志 | 含义 | 该做什么 |
|---|---|---|
| `检索跳过：… 没有可用索引（原因）（字段 X）` | 索引不可用（指纹不符 / 文件损坏） | 重建，或换回建库时的模型 |
| `索引待重建（…）：… —— 点「建索引/重建索引」即可` | 索引是**故意**写下的半份（建库时有条目失败） | 点重建 |
| `索引只编到 N/M 条（上次中途结束）—— 点「建索引」接着编即可` | 半份且**可续**（建库途中被杀，指纹一致） | 点「建索引」**接着编** |
| `查询向量编码失败（本轮不注入）：… —— 与索引无关，重试即可` | **偶发**（模型/内存状态） | 重试，**别动索引** |
| `检索 0 条命中（最高分 X / 阈值 Y），不注入` | 库里确实没有相关内容 | 调阈值 / 加内容 |

其中**最高分是"过滤之前"的**：`0.281 / 阈值 0.350` = 差一点，`0.047 / 阈值 0.350` = 完全不像。

**可判别性**：注入片段以 `[知识库]` 起头、**每条一行纯正文**（行尾不拼来源尾巴 ——
prompt 里有什么模型就可能抄什么，于是回答里会冒出那段元信息）。

| 动作 | 行为 |
|---|---|
| 点库列表里的某个库 | 设为当前库 + **把它的正文读进文本框**（有未保存改动时先问） |
| 「保存正文」 | 只写 `texts.jsonl`（毫秒级），**不重算向量**（但会让索引失效） |
| 「建索引/重建索引」 | 落盘 + 逐条重算向量（条数 ≥ 200 时先弹一句"要多久"） |
| 「追加」 | **只编码这一条**，向量接到索引末尾，其余向量原位保留，**无需重建** |
| 条目列表里的「删」 | 正文与向量**同时**移掉那一行，后面的行号前移一位（不可撤销） |

保存正文**会让索引失效**（指纹里的正文 hash 对不上了）—— 状态行与库列表都会明确写出
「正文已改：需重建」，检索随之停用，这一条刻意**不做成静默**。反过来说，正文没改时保存是**幂等**的。

**离线判据**：`run_rag_inject_tests.sh` / `run_rag_inject_guard.sh`（检索注入与格式对齐）、
`run_rag_edit_guard.sh`（正文编辑闭环）、`run_rag_entry_guard.sh`（条目编辑）、
`run_rag_archive_guard.sh` + `run_rag_archive_tests.sh`（正文导入 / 导出）、
`run_rag_cost_tests.sh` / `run_rag_progress_tests.sh`（成本提示与进度读数）。

### 远端使用知识库 + `/v1/embeddings`

两条**互不相干**的路，一起上线但刻意**解耦**：

**① 远端注入**：「知识库」页新增「允许远端（HTTP）调用使用知识库（**默认关**）」+ 一个
**独立的「远端库名」**。开了之后，`/v1/chat/completions` 会把检索到的片段按与
App 内**同一个位置**（最后一条 user 之前）注入。

```bash
curl -s http://<手机IP>:<端口>/v1/chat/completions -H 'Content-Type: application/json' -d '{
  "messages":[{"role":"user","content":"我们的退货政策是几天？"}]}'
# 注入了时，响应里多一个字段（没注入时**一个字节都不多**）：
#   "local_rag":{"kb":"售后","injected":3}
# 回答正文里也有可判别锚点：以 `[知识库]` 起头、每条一行纯正文（不含来源尾巴）
curl -s http://<手机IP>:<端口>/health
# -> ...,"rag_remote_enabled":true,"rag_remote_kb":"售后","rag_remote_injected":3
```

- **为什么默认关**：远端是**无状态**的，服务端不知道调用方想不想要。默认注入 =
  用调用方没要求过的内容污染回答，而接口照 200。
- **为什么远端库名要独立**：`currentKb` 是单一全局值，在 App 里点任何一条库都会改它。
  若远端跟着它走，就会出现"你在 App 里切到库 B 看了两眼，远端某个正在轮询的客户端**静默**换成了库 B"。
- **协议层可见（这是安全阀）**：正文里的 `[知识库]` 锚点 / 响应里的 `local_rag` 字段 /
  `/health` 的三个 `rag_*` 字段（发请求前就能读）。
- **没有"临时关闭"的请求侧口子**：要不要注入只在 App 内那个开关上。
- 远端日志每次注入/未注入都留痕。

**② `/v1/embeddings`**：无状态、逐条把文本编码成**已 L2 归一化**的向量。

```bash
curl -s http://<手机IP>:<端口>/v1/embeddings -H 'Content-Type: application/json' -d '{
  "model":"bge-small-zh-v1.5","input":["苹果富含维C","香蕉富含钾"]}'
# -> {"object":"list","data":[{"object":"embedding","index":0,"embedding":[...384 个数...]}, ...],
#     "model":"bge-small-zh-v1.5"}
```

`input` 支持四种形态：`"一句话"` / `["a","b"]` / **token id 数组** / **二维 token 数组**。
`encoding_format` 支持 `float`（默认）与 **`base64`**。

```bash
# base64：每维 4 字节小端 float32，整段一起 base64（384 维 -> 2048 字符）
curl -s http://<手机IP>:<端口>/v1/embeddings -H 'Content-Type: application/json' -d '{
  "model":"bge-small-zh-v1.5","input":["苹果"],"encoding_format":"base64"}'
# -> {"object":"list","data":[{"object":"embedding","index":0,"embedding":"qLcav..."}], ...}
# Python 解回来（小端、float32、按 384 维 reshape）：
#   import base64, numpy as np
#   v = np.frombuffer(base64.b64decode(d["embedding"]), dtype="<f4")
```

- **与知识库开关完全解耦**：这个端点只判"嵌入模型在不在"（缺了 `503` + 明文原因），
  **不读**任何 `rag_*` 开关。
- **已归一化**且按模型声明的池化方式取值；归一化口径与内部检索**同一份**。
- **`input` 支持 token id 数组**：id 用**嵌入模型自己的 vocab** 还原成文本。**越界的 id 整条 400**
  （不 clamp、不跳过）。混排（`[1,"a"]`、`[1,[2,3]]`）一律 400。
- **`dimensions` 明确 400**（不静默忽略）：本地嵌入模型没有 MRL 结构，截断出来的向量语义是坏的。
  `dimensions: null` 与"字段缺失"同义，不拒。
- **`input` 条数/单条超限直接 400**（不是截断）：截断会让 `data` 与你给的文本**错位**，而错位不报错。
- **一条失败不拖垮整批**：那一项回 `embedding:null` + `error` 说明，`index` 仍对齐。
  `input: []` 是**合法**的（回空 `data`）。
- 不伪造 `usage`：拿不到真实 token 数就**不报这个字段**。

⚠ **一条口径契约**：`rows`（正文按换行切出的**段数**）与索引里的 `count`（条目数）**差恒为 1**
（编码总以换行收尾）。两者写成相等会让每一份正常索引都被判成"索引落后于正文"。

**索引必须连正文一起落盘**：只有向量的索引能说出"命中了第 3 条"，却拿不出第 3 条是什么。
正文落在 `texts.jsonl`，与索引**同生同死**。

**离线判据**：`run_rag_remote_guard.sh`（远端开关默认 false / 库名独立 / 注入接线）、
`run_rag_remote_tests.sh`（`/v1/embeddings` 的 index 对齐 / base64 字节序 / token id 还原）、
`run_embed_params_guard.sh`（三个协议参数的接线）。

### 结构化输出（`response_format` / JSON Schema）

`json_object`（要合法 JSON、不限结构）与 `json_schema`（按给定 JSON Schema 约束输出），
约束走 **GBNF grammar 采样器**，在生成循环里逐个 token 生效。

```bash
curl -s http://<手机IP>:<端口>/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{
    "messages":[{"role":"user","content":"把张三、30 岁、北京整理成 JSON"}],
    "response_format":{"type":"json_schema","json_schema":{
      "name":"person","strict":true,
      "schema":{"type":"object",
                "properties":{"name":{"type":"string"},
                              "age":{"type":"integer"},
                              "city":{"type":"string"}},
                "required":["name","age","city"]}}}
  }'
```

- `type` 拼错 / 类型不对 / 包装缺字段 / schema 不是对象 / schema 超过 64 KiB → **`400`**。
- 库能接受但转换不出 GBNF → **`200` + 降级成无约束**，并在 App 日志写明原因。
- 要求了结构化输出时，服务端在下发前把模型自由写出的 Markdown 代码围栏剥掉：
  **剥了还得是 JSON，剥不了就原样下发**。⚠ 只对非流式与缓冲流式（带 `tools`）生效。

**「思考开 + `json_schema`」是一处已知的语义冲突**：模板要求先写思考段，而 grammar 要求
生成前缀之后**直接**是 JSON。默认关闭思考，常态下不会遇到。

**离线判据**：`run_json_schema_tests.sh`（请求侧解析/校验）、`run_schema_sampler_guard.sh`（接线）。

### 自带测试页（`GET /`）

浏览器直接打开 `http://<手机IP>:<端口>/` 就能用，**同源、零外部依赖**（不引任何 CDN）。
页面本体是 `WebChatPage.kt` 的**纯函数产物**，所以页面结构能被宿主侧**离线断言**，
不必等真机打开浏览器才发现少了一个 `id`。折叠设置区（原生 `<details>`，**默认收起，四组**）：

- **思考链**（`enable_thinking`）：三态 —— **跟随服务端默认 / 开 / 关**。「跟随」= **不下发该字段**。
- **生成与采样**：`temperature`、`top_p`、`top_k`、`min_p`、`max_tokens`、`seed`。
- **重复与惩罚**：`repeat_penalty`、`repeat_last_n`、`frequency_penalty`、`presence_penalty`。
- **结构化输出**（`response_format`）：**不要求 / `json_object` / `json_schema`**。

字段名与服务端请求侧逐字一致，**留空的项不下发**，由服务端取默认值。填了非法值则**整个请求不发出**。
页面顶部按 `model_loaded` 提示是否已加载模型。

**多轮连贯对话**：服务端无状态，连贯性由页面自己维护历史。两条硬判据：
**只有成功的回复才进历史**、**「新对话」同时清历史与已渲染的气泡**。token 输入框留空则不发 `Authorization` 头。

**单条删除**：长按（桌面端右键）任一条气泡可**只删这一条**，不连带删配对的那一条。

**三页横向切换**：顶部分「聊天 / 设置 / 探测」三页，页签点击与左右滑动**两个入口都要**。
滑动的落点是内容节点而不是 `document`（页面里有 `textarea`，挂在 `document` 上会抢走光标移动）。

**重新生成**：长按**最后一条**气泡 → 菜单里的「重新生成这一条」。语义是**从这条往下重跑**：
长按 assistant = 重写答案；长按 user = 这一句重新问一遍。**不是最后一条时不给这个出口**。

**离线判据**：`run_web_chat_tests.sh` 与 `run_web_chat_guard.sh`。

### App 内聊天页（气泡 · 单条删除 · 四页）

消息渲染是**一条一个气泡 View**（`chatContainer`），不是"一个 `TextView` 拼全部"。要点：

- **流式只改"正在生成的那一条"的文本**，不重建整屏（长会话下每 token 重建几十个 View 会卡）。
- **长按任一条气泡可单独删除**，下标必须**当场反查**（`chatBubbles.indexOf`），不能在闭包里捕获。
- **气泡本体要有可见形状**（圆角 + 底色），**不是只有左右缩进**。
- **正文不可选中**（否则长按会被"选文字"吃掉，外层气泡的长按监听永远收不到）。"复制"从长按菜单走。
- **删除 / 清空之后作废 KV 账本**。

配套：左右滑动在「聊天 / 设置 / 知识库 / 调试」四页间切换（知识库设置自设置页拆出独立成页）。

**聊天记录导入 / 导出**（会话管理对话框与长按菜单）：导出走**独立信封**而不是复用
`s_<id>.json` 的内部格式。「导入」的入口在会话管理对话框的标题栏上、**与它的对偶「导出全部」同一层**。

```json
{ "format": "local-llm-chat", "version": 1, "exportedAt": 1760000000000,
  "sessions": [ { "id", "title", "system", "createdAt", "updatedAt",
                  "messages": [ { "role", "content" } ] } ] }
```

四条口径都是**为了防止"错得不响"**：

- `format` / `version` 对不上就**拒绝**，不做"尽力解析"。拒绝时文案带上实际读到的 `format`。
- 导入**只增不改**：每条都是**新会话**（新 id），绝不按原 id 覆盖。重名按**标题**去重。
- 脏 `role` 跳过**并计数**（历史是直接喂模型的，别的 role 会被当**指令**执行）。
- **导出不做裁剪**，导出的语义就是"原样带走"。

落盘 MIME 显式声明 `application/json`。会话文件的布局只在 `SessionStore` 一处。

**旧会话迁移被配额挡住时会出声**：`BLOCKED_BY_LIMIT` 会落成聊天页顶部一行**常驻**提示
（不是 Toast —— 冷启动那一瞬漏掉就再也不会出现）。旧文件**不删**。
「本来就没有旧会话文件」与「迁成功了」**都不出声**。

**会话库的配额**：上限是**正文总字符数**，不是会话个数（个数与被在意的资源都不是线性关系）。

- **硬闸门 `MAX_TOTAL_CHARS = 2_000_000`**：新增（`create` / 导入 / 迁移）时判定；超了**明确拒绝**
  并报出"已用 X / 上限 Y"，**不**静默截断、**不**自动删最旧。
- **软提示 `MAX_SESSIONS_WARN = 200`**：只提醒，**不阻止**任何操作。
- **只卡新增，不卡已存在**：读路径永不因超限拒绝（否则老库会陷入"打不开也删不掉"的死锁）。
- **导入按预算从前往后收**，收不下就**停在那一份上**，收了几条如实报出。

**会话列表的搜索与按时间批量清理**：

- **搜索**：按**标题**做子串匹配、忽略大小写、**输入即筛**。只搜标题不搜正文（正文匹配要在主线程读全文，会卡顿）。
- **批量清理**：长按会话 → 「🧹 批量清理…」→ 选档位（**7 / 30 / 90 天**）→ **逐条勾选** → 删除。
- **默认一个都不勾**（批量删不可恢复，而"多少天算旧"这条线从来不会与用户心里的那个日子刚好对齐）。
- **「删除」是视图里的自有按钮，不占 `setPositiveButton` 的位置** —— 可用性由
  **一个**能在宿主上被穷举的函数（`SessionCleanup.canDelete`）决定。
- **候选列表不含当前会话**。
- **筛选只是渲染层的取数**：删除/导出一律重新取全库。
- **删完作废 KV 账本**（被删的会话里可能正有一条是"当前会话的前身"）。
- **「多少天算旧」是闭区间**；`updatedAt <= 0` 同样**算旧**。

列表的实现上有一处要点：会话管理用自持的 `BaseAdapter` 装 `SessionStore.Info` 本身，
点击/长按拿到的**永远是 Info**（用 `ArrayAdapter<String>` 再按下标去对，筛选后就错位了）。

**喂给模型的历史有两条保险丝**（只在写入路径 `SessionStore.append` 上生效）：

- **条数 `MAX_MSGS = 40`**（= 20 轮问答）：超出从**最早**的丢。
- **字符 `MAX_CHARS = 24000`**：分两级 —— 先丢最早的历史（丢到 `MIN_MSGS = 2` 条为止），
  仍超限时再从**次新**的往前收窄。

**末条整体保留**，不做"保头截尾"（截它就是"我贴的代码它只看到一半，还答得头头是道"）。

**离线判据**：`run_chat_bubble_guard.sh` / `run_chat_regen_guard.sh`、
`run_session_cap_guard.sh` / `run_session_migrate_guard.sh` / `run_session_quota_guard.sh`、
`run_session_cleanup_guard.sh`、`run_chat_archive_guard.sh`。

### 调试页（原「日志」）

页签名是**「调试」而不是「日志」**：这一页装的东西（崩溃取证开关、导出崩溃探针、
纯 CPU 加载、日志正文与筛选）**共同的判据是"只在出问题的时候才有用"**，
一条都不回答"服务起来没有"。叫「日志」会让人以为这里只有滚动文本；
叫「调试与运行」则在标题上承诺了它做不到的事。

**排障入口都收在这一页**，与"真配置"分开：设置页留下的都是"调了有可感知收益"的参数。

**日志筛选：标签多选 + 任意关键字**，两个维度**可以叠加**：

- **标签多选**：**计时 / 内存 / HTP / 仅错误**。**一个都不选 = 全部**（界面上没有「全部」这一档）。
- **任意关键字**：输入即筛（没有"搜索"按钮），**子串、忽略大小写**，带一键清空。

两个维度之间是**与**。选中的档位与关键字都记进 `ui_prefs`。几条硬约束：

- **筛选发生在 ring（2000 行）上，不在已渲染的 120 行上**。
- **导出与崩溃现场不筛**。
- **空白页要说清是哪种空**（没命中时显示"没有同时满足…的日志行，整段共 N 行"）。
- **标签与失败标记都看行首**（关键字除外）。「仅错误」认行内的 `⚠`。

**模型档案：`GET /v1/models/{id}` 与 `[模型档案]` 日志行**。`/v1/models` 的每条 `data[]` 里
多了一个可选的 `profile` 对象，当前加载的那个模型才带它。

```console
$ curl -s localhost:8080/v1/models/qwen3-0.6b | python3 -m json.tool
{
  "id": "qwen3-0.6b",
  "object": "model",
  "owned_by": "local-llm-server",
  "meta":   { "size": 397903264, "ftype": "Q8_0" },
  "profile": {
    "name": "Qwen3-0.6B",
    "architecture": "qwen3",
    "tensor_bytes": 375000000,
    "param_count": 596049920,
    "ctx_train": 40960,
    "vocab_size": 151936,
    "file_type": "7",
    "meta_count": 37
  }
}
```

| 数 | 含义 | 别和谁混 |
|---|---|---|
| `meta.size` | **文件字节** | 含元数据 / 词表 / 对齐填充 |
| `profile.tensor_bytes` | **权重张量字节** | 与上一行的差就是那些填充 |
| `profile.param_count` | 参数**个数** | 与"文件多大"无关 |
| `profile.ctx_train` | 模型**训练时**声明的上下文上限 | ≠ 你在设置页设的 `n_ctx` |

三条边界：**每个数各自可缺**（取不到的字段整个不出现，不是 `0`）；**档案不缓存**；
**档案只描述"当前加载的那一个"**。

### 浏览器 / CORS（白名单式）

服务端每个响应都带 CORS 头、`OPTIONS` 统一回 `204`。默认放行**回环来源**
（`http://localhost:*`、`http://127.0.0.1:*`、`http://[::1]:*`）、**`Origin: null`**
与**本机 IP** 的来源。其余来源一律不回 CORS 头。要放行局域网内另一台机器上的前端
（例如 PC 上的 Open WebUI），在设置页「CORS」那一栏按行填来源，改完立刻生效。

**刻意不做、也不要自己加上去的两件事：**

- **不用 `Access-Control-Allow-Origin: *`**。本接口**无鉴权**，一旦回 `*`，攻击面立刻变成
  「你在浏览器里打开的任何一个网页都能调这台手机的模型」。
- **不发 `Access-Control-Allow-Credentials`**。

白名单外的来源**回 204 而不是 403**：头缺失本身就是拒绝，而 403 会让"来源被拒"与"服务坏了"
在客户端看起来一模一样。来源被拒时服务端日志会有 `CORS 拒绝来源: …` 一行。

**两件容易混的事，它们是独立的：**

| 你要的效果 | 靠什么 | 需要 CORS 吗 |
|---|---|---|
| 打开 `http://<手机IP>:<端口>/` 直接聊 | `GET /` 自带测试页（**同源**，支持多轮） | **不需要**。同源页面根本不查 CORS |
| 让跑在**别的源**上的前端（Open WebUI 等）调这台手机 | CORS 白名单 | 需要，且要把它填进白名单 |
| 让**没带凭据的调用方**调不动生成端点 | 鉴权（`Authorization: Bearer`） | 不需要 |

另有一条硬约束：`OPTIONS` **必须豁免鉴权**。

### App 内「存活探测」

设置页「启动服务」旁的**存活探测**按钮会从 App 内真发一次 `GET /health`，把结论常驻显示在按钮下方：

| 结论 | 含义 |
|---|---|
| ✅ 存活 | 端口可达、`status=ok`、模型已加载 —— 现在就能推理 |
| ⚠ 可达但状态不完整 | 端口通了，但 `status` 非 `ok`、或**模型未加载**（生成类请求会返回 503） |
| ❌ 不可达 | 连接被拒 / 读超时 / 应答的不是本服务（正文不是 JSON） |

它**不看** `HttpApi.isRunning` 这类进程内标志位：那些只说明对象自认为在跑，说明不了端口真可达。

### 工具调用（tools / function calling）

`/v1/chat/completions` 认 OpenAI 的 `tools`，命中时 `finish_reason` 为 `tool_calls`，
`message.tool_calls[].function.arguments` 是 JSON 字符串；`stream=true` 时按 OpenAI 约定
以增量块下发。`tool_choice`（`auto`/`required`/`none`）与 `parallel_tool_calls` 均生效。

- 工具调用语法**由模型模板决定**（Qwen 的 `<tool_call>`、Llama 的 `[TOOL_CALLS]` 等），
  Kotlin 侧不做正则猜测。模板不支持工具调用、或渲染失败时**回落到普通对话**；
  `tools` 不是数组（如写成对象）才返回 `400`。
- 带 `tools` 的流式请求会**整段生成完再下发**，因此首字延迟等于整段生成时间。

```bash
curl -s http://<手机IP>:<端口>/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{"messages":[{"role":"user","content":"北京现在天气怎么样"}],
       "tools":[{"type":"function","function":{
          "name":"get_weather","description":"查询指定城市天气",
          "parameters":{"type":"object",
            "properties":{"city":{"type":"string"}},"required":["city"]}}}]}'
```

### 默认关闭思考

设置页的「默认关闭思考」勾选框在**「生成与采样」分组内**。两条生效路径：**模板自带
`enable_thinking` 变量时交给模板自己关**；**模板里没有这个变量时，才由软开关兜底**。
请求侧覆盖优先级：`enable_thinking` > `chat_template_kwargs.enable_thinking` >
`reasoning_effort`（`none` 视为关）> 全局默认。App 内聊天与 HTTP 接口**共用同一份实现**。

### 输出的思考段 / 正文分流

生成结果按 `<think>` 标签切成两路：思考段进 `reasoning_content`，正文进 `content`，
HTTP 的流式与非流式共用同一份实现。判据是「后缀里有一个**未闭合**的 `<think>`」。

## 支持的后端与机型

推理核心不自建，直接用 [Vali-98/cui-llama.rn](https://github.com/Vali-98/cui-llama.rn) 的
预编译产物（`vendor/`，未做任何二进制改写）。启动时逐个尝试，任一失败即降级：

| 顺序 | 需要条件 | 后端能力 |
|---|---|---|
| 1 | **高通** SoC **且** i8mm **且** 有 `libOpenCL.so` | CPU + OpenCL GPU + Hexagon NPU |
| 2 | i8mm | 纯 CPU |
| 3 | dotprod | 纯 CPU |
| 4 | 无（基线） | 纯 CPU |

第 4 档不可省：骁龙 865/870（Cortex-A77）连 dotprod 都没有，缺基线包会直接闪退。
判定只看内核导出的 CPU 特性，**只保守不冒进**（漏报就退回低档）。加载结果写在日志首行，可核对。

## Hexagon NPU（可选，默认关）

开启三步：设置里打开 HTP → **重启 App** → 加载时确认日志显示 HTP 生效。
缺任一条件都会静默回退，不影响使用。要点与排查见 **[docs/HTP.md](docs/HTP.md)**。一句话结论：

> NPU 上**不一定**比 CPU 快。小模型（约 ≤4B）CPU 往往更优；NPU 的价值在于长 prompt 的 prefill
> 与把权重从 GPU 显存挪开。UI 里的「NPU 配额档」不是性能旋钮，只用于腾挪显存/排查，建议保持「自动」。

## 已知限制

- 仅 `arm64-v8a`；只提供 **debug** 构建（release 需先解决签名与 minify 配置）。
- **单并发**：同一时刻只跑一轮生成，第二个请求直接 `503`、不排队；`parallelN` 填 >1 只会按份数瓜分 `n_ctx`，建议保持 1。
- 结构化输出受模型模板能力约束，转换不出 GBNF 时降级成无约束（日志留痕）。
- **「思考开 + `json_schema`」的语义冲突尚未处理**：默认关闭思考，常态下不会遇到。
- `gpuLayers > 0` 且 `n_ctx > 32768` 时 OpenCL compute buffer 可能分配失败；失败会**自动回退纯 CPU**。
- HTP 后端对部分算子/量化不支持 → 静默回退 CPU；算子只落在 HTP0 单核。
- 长 prompt **首轮** prefill 可能几十秒级，期间界面只有日志在动，没有百分比进度。之后多轮走 KV 前缀复用。换模型 / 改 system 提示词后回到首轮代价。
- **CORS 不是访问控制**：白名单只决定"浏览器肯不肯把这个响应交给页面"，任何绕过浏览器的客户端从来不受 CORS 约束。
- **鉴权也不是访问控制**：token 挡住的是"没带凭据的调用方"，**挡不住同网段能直连的设备**（token 走明文 HTTP）。默认不开，请在可信网络使用。
- **对话模型仍是一次一个**；嵌入模型可与之**双常驻**。换对话模型走卸载重载，但**不动**嵌入模型。内存若未归还，重启 App 是最快恢复手段。
- **RAG 的远端入口已做，但刻意不支持"请求侧临时关闭"**：`/v1/chat/completions`
  **不认** `knowledge_base` 字段（只认 App 内那个远端开关），也不提供 `X-No-KB` 之类的口子。
- **`/v1/embeddings` 需要先加载嵌入模型**：没加载就 `503` + 明文原因，绝不静默回空向量。它**不读**知识库开关。
- **`/v1/embeddings` 单并发执行**：与检索共用 `embedLock`（但**不占**生成路径的 `genLock`），所以两个 embeddings 请求会串行。
- **`/v1/embeddings` 不支持 `dimensions`**（明确 400）：本地嵌入模型没有 MRL 结构。要降维请在客户端做。
- **`/v1/embeddings` 的 token id 数组必须来自同一份嵌入模型**：越界的 id 整条拒，不 clamp、不跳过。
- **RAG 注入与 KV 前缀复用的相互作用**：注入块每轮都变，所以开了远端知识库后，多轮对话的公共前缀会从"本轮提问处"开始分叉 —— 这是语义决定的，不是 bug。
- **索引只作用于"当前一份"嵌入模型，且与正文绑定**：换模型 / 改切块参数 / **改正文** / **改批大小**即作废重建。
- **「保存正文」后检索会停用，直到重建**：正文与向量是一对。状态行与库列表都会写出「正文已改：需重建」。
- **追加只能在末尾、删除只能整行、没有"中间插入"和"撤销"**：中间插入等于全量重写。编辑器里改任意一行再「建索引/重建索引」才是插入的正路。
- **追加不做分块**：超过一块大小（默认 480 字）的文本会被**截到一块**并在日志里说清。
- **双常驻 ≠ 免加载**：模型随进程被杀归零，持久化解决的是**索引**，不是**模型**。
- **mmap 与 GPU/NPU 不互斥**：CPU 层走内存映射，GPU/NPU 层本来就要拷进显存。改动后需重新加载模型生效，实际档位记在日志 `[加载]` / `[mmap诊断]` / `[mmap池]` 几行。
- **mmap 省内存是"加载后归还"实现的**：本仓库在加载完成后把预读进来的干净页还给内核（日志 `[mmap释放] RSS A MB → B MB`）。
- **mmap 在共享存储上能否省内存，分机型**：取决于该挂载是否走 **FUSE passthrough**。判据看同一轮的 `[mmap释放]` 读数：**RSS 真落下来即共享**。
- **权重重排（repack）是另一个占内存的默认值**：q4_K/q6_K 会被重排成 `q4_K_8x8`/`q6_K_8x8`
  **另存一份匿名内存**。**这不是量化**：盘上的权重一个字节没变。设置页三档单选：
  **没设过（跟随库默认 = 开）/ 关 / 开**，**默认保持开启**。日志里 `[repack]` 与 `[repack结果]` **成对读**。
- **`free` ≠ RSS 下降**：CPU 侧分配器会缓存刚释放的堆段。本仓库在「卸载模型」这一步主动把空闲堆段还给内核。
- **退出 App 会主动释放模型**：真退出且 HTTP 服务**没在跑**时自动释放。
- **推理期也有 RSS 读数**：一轮生成收尾会打 `[内存] 推理期 RSS 峰值 … MB`，与 `[mmap释放]` **成对读**。三行都读 **VmRSS**。
- 前台服务用于保活，部分国产 ROM 仍会杀后台/冻后台，需要自行加白名单；被冻过的痕迹见 `/health` 的 `frozen_*` 字段。

## 角色卡（V1）

聊天页 `system` 输入框上方多了一行：**角色卡**（下拉 + 「管理卡片」）。它做的事只有一件 ——
**给会话的 `system` 起个名字**，让一段设定可以点一下就复用。

**卡片就是那段 `system` 文本**，没有别的任何东西：没有分区、没有占位符替换、没有首条消息 /
备用问候 / 示例消息（那是 V2，本版明确不做）。三条口径：

- **会话存的是内容快照，不是一个 id。** 卡片被删/被改名之后，用了它的会话**照旧能正常聊天**。
- **改了卡片，已挂卡的会话不会跟着变。** 聊天页那一行会常驻显示"卡片已修改，本会话用着挂卡时的内容"。
- **切卡会作废 prompt 缓存（KV 前缀）。** `system` 在 pos 0，前缀是逐 token 比的 —— 换了它命中长度就是 0。

卡片库是**整体重写**，所以写盘走"先写 `.tmp` 再 rename"（直接 `writeText` 写一半断电 =
整个卡片库变成半截 JSON = **全部卡片一起没**）。

卡片**不进会话配额**，但单独有两条线 —— 最多 200 张（`RoleCard.MAX_CARDS`）、
单张正文最多 24000 字符（`RoleCard.MAX_CARD_CHARS`），超了**明确拒绝**并说清是哪一条超了。

**离线判据**：`run_role_card_guard.sh` + `run_role_card_tests.sh`。

|---|---|
| GGUF 模型 | `<getExternalFilesDir(null)>/models/*.gguf`（外部存储不可用时回落到 `<filesDir>/models`） |

| 运行日志 | `<filesDir>/logs/session-<启动时间>.log`，保留最近 8 个会话 |
| 导出日志 | 调试页「导出本次 / 上次会话」→ 公共「下载」目录（API 29+ 走 MediaStore，无需权限）。**导出不受调试页筛选影响** |
| 聊天记录导入导出 | 会话管理「导出全部」/ 长按会话「导出这一条」→ 公共「下载」目录，`chat[-all][-<id>]-<时间>.json`（独立信封，`format=local-llm-chat`）；**「导入」在会话管理的标题栏上，与「导出全部」同层**，从公共存储读回。**导出不受任何界面状态影响，导入只增不改**；信封里的 `system` 是**实际生效的那一段** |
| 会话列表搜索/清理 | 会话管理对话框顶部**搜索框**（按标题、忽略大小写、输入即筛）；长按会话「🧹 批量清理…」→ 按 7/30/90 天列候选 → **逐条勾选**后才可删（默认不勾、不含当前会话） |
| 旧会话迁移 | 旧版单会话文件 `<filesDir>/chat_session.json` 在首次启动时迁成「会话 1」；**被上限挡住时聊天页顶部常驻一行提示**，旧文件留在原地、下次启动自动重试 |
| 崩溃现场 | `<getExternalFilesDir(null)>/crash_last.txt` |
| native 崩溃取证 | `filesDir/logs/probe-native.log`（**调试页**「崩溃取证模式」打开后由 native 直写：native 全量日志 + stderr 遗言 + 逐 token 原始流 + 信号现场） |
| 参数/端口/别名 | `SharedPreferences`（经 `ModelStore`） |

## 构建

**质量门禁：`.cnb.yml`（CNB 流水线）** —— 仓库里唯一的**质量**门禁，一把跑完 `tools/` 下的
全部离线套件（各个模块守卫、守卫自测、行为复刻对照）。改任何源码、守卫或文档，都在这里被拦。

**APK 分发链路：`.github/workflows/build.yml`（GitHub Actions）** —— 与上一条是**两条**职责不同的流水线。
只做构建，**不跑任何**
`tools/run_*`。push 到 `main` 且改动影响 APK 时构建，也可手动触发；
纯文档与工具类改动（`**.md`、`docs/**`、`scripts/**`、`tools/**`、`.gitignore`、`LICENSE`）
由 `paths-ignore` 排除，不触发构建。注意这条 `paths-ignore` 是 **GitHub workflow 自己的**行为，
与 `.cnb.yml` 无关 —— 改 `tools/**` 不会触发 APK 构建，但 `.cnb.yml` 那侧照跑。

**本地构建**：Android Studio 或自备 Gradle 8.10.2（仓库不含 wrapper）。`compileSdk 35` /
`minSdk 26` / `targetSdk 28` / AGP 8.7.3 / Kotlin 2.0.21 / C++17 / `ANDROID_STL=c++_static`。
`settings.gradle.kts` 把国内镜像排在最前、官方源只作兜底。

**离线单测**：不装机、不下载模型也能跑的单测都在 `tools/run_*.sh`，覆盖采样与停止序列语义、
请求取消、KV 前缀复用、嵌入向量（归一化 / 池化 / 检索）与双常驻隔离、嵌入入口与探活接线、
思考开关与正文分流、结构化输出的解析与接线、CORS 与鉴权、崩溃探针、mmap 开关接线等；
没有 NDK 也能做真实类型检查：`bash scripts/kt_check.sh`。

## 排查 native 闪退（崩溃探针）

native 侧的 `abort`（SIGABRT）由 libc 直接终止进程，**不经过 JVM**，所以
`UncaughtExceptionHandler` 抓不到它。用法三步：

1. 调试页顶部打开「崩溃取证模式」，**完全退出并重启 App**（探针在 native
   库加载前挂载，必须冷启动才生效）。
2. 复现那次请求（客户端带 `tools` 调一次）。
3. 重开 App → 调试页 →「导出崩溃探针」→ 公共「下载」目录拿到 `probe-<时间戳>.txt`。

导出的文件是三段合一：native 探针原文、Kotlin 侧本次会话全文、上次会话全文，末尾附设备/后端/Boot ID。

**两份日志的分工**：取证模式开着时，`probe-native.log` 收 native 全量 + stderr 遗言 + 逐 token 原始流 + 信号现场；
`session-*.log` 同时保留 Kotlin 侧全量（**不折叠**）。两份合起来才是全量。
探针关闭时开销为零。开关有唯一的事实来源（调试页），native 侧在 `JNI_OnLoad` 里还会先自举一次，
自举阶段**只记不写**（不打开文件、不落盘），所以探针没启用时自举记的事件**不建文件、不落盘**、
只进 logcat。Kotlin 侧**「关」也会显式告知 native**。

**文件是"每代一份"，不是从安装累积到现在**：每次冷启动把上一份滚成 `probe-native.log.prev`，
本代从零开始写。只留**两代**。`session-*.log` 保留最近 `LogFileStore.KEEP`（8）个会话，
排序口径是**文件名里的时间戳**，不是 mtime。

**目前没有体积上限**：上限值要先有实测数据。所以探针文件会一直长，嫌占地方就关开关或直接删文件。

**离线判据**：`run_probe_switch_guard.sh`、`run_probe_signal_guard.sh`。
